# STRATA 数智教学系统

STRATA 2.0 是一套面向中学课堂的教学系统。老师可以用它备课、上课、组织活动、布置测试、收作业和做过程评价；学生可以在课堂中查看资源、完成题目、提交作品并参加小组学习。

系统安装在学校自己的服务器上，教师机和学生机通过校园局域网访问。日常教学数据保存在校内，不要求上传到公共云平台。

项目目前仍在开发和学校试用阶段。现有页面和主要教学流程已经可以运行，分层、分组和模型功能已经用模拟数据跑通，但还不能把模拟结果当作真实教学效果。

## 先看这几件事

- 普通备课和上课不需要 AI，也不需要 ONLYOFFICE。
- 教师可以自愿填写自己的 DeepSeek API，用来辅助出题、修改学习网页和整理备课内容。
- 安装 ONLYOFFICE 后，可以在网页中预览和协作编辑 Word、PPT、Excel；没有安装时，其他功能仍可使用。
- 学生看不到系统内部的 A/B/C 层级、模型概率和班级排名。
- 系统只向老师提供建议，不能自动给学生分层、调班、处分或降低学习要求。
- 每个小组的共享文件空间默认是 **20 MB**，老师可以按课堂任务调整。

## 老师怎样完成一节课

### 1. 建立课程

老师先在“课程备课”中建立课程，选择自己任教的班级。课程可以上传封面；没有封面时，系统会使用带课程名称的默认图片。

### 2. 设计课时

每个课时由若干学习环节组成。老师可以按实际教学顺序加入：

- PPT、Word、PDF、Excel、视频、图片、链接和压缩包等资源。
- 单选题、多选题、判断题、填空题和主观题。
- 需要学生上传文件的作品或任务。
- AI 辅助生成的学习网页和网页表单。
- 自评、互评和教师评价内容。

资源和题目可以分别排序。一个环节里可以同时放资源和题目，例如学生左侧查看课件，右侧完成本环节的课堂题。

### 3. 新建课堂

老师在“课堂教学”中选择课程、课时和班级，建立本次课堂。没有开始的课堂，学生不能进入；老师开始课堂并投放环节后，学生才能看到相应内容。

### 4. 课堂控制

课堂控制台以整页方式打开，老师可以：

- 逐个投放、关闭和切换学习环节。
- 发起签到，并把学生标记为正常、迟到、请假或缺勤。
- 随机点名，给被点到的学生课堂反馈。
- 发起抢答，并在学生抢答后加分、减分或不处理。
- 设置倒计时，学生端同步显示剩余时间。
- 发送课堂广播，学生端即时弹出消息。
- 查看每道题有多少学生完成、哪些答案正确。
- 查看学生上传的附件，并进行预览、评分和评价。
- 开启实名文字聊天和小组合作。
- 在课堂收尾时开启自评、互评或教师评价。

### 5. 课后查看

课堂结束后，老师可以查看学生的作答、附件、测试、评价、课堂表现和近期学习情况。系统会把零散记录整理为当日、近 7 日、近 30 日和单元学习情况，帮助老师决定后续要补什么、练什么或提供什么支持。

## 课堂里还有哪些功能

### 小组合作

老师可以为正在进行的课堂开启小组合作，选择 Word、PPT 或 Excel 作为协作文档，也可以允许小组共享文件。

每组共享空间默认 **20 MB**。项目日志、甘特图、阶段成果等材料不是必填项，老师可以根据任务需要选择使用。

### 实名文字聊天

聊天只绑定正在进行的课堂，每节课堂默认关闭。老师可以分别开启：

- **全班聊天**：老师始终可以发言；老师开放后，学生也可以参与。
- **与老师聊天**：学生和老师一对一交流，其他学生看不到。
- **小组聊天**：只有本组学生和老师可以查看，老师可以进入任意小组。

平台不提供学生之间的一对一私聊。

可疑言论会先进入教师审核，不直接向其他学生公开。老师可以选择放行、警告、撤回或扣分。警告和扣分不会自动执行，必须由老师确认。

### 评价

评价内容由任课教师制定，不由学校管理员统一替老师填写。

- “评价标准”页面负责制定和发布评价内容。
- “课时设计”负责选择本课使用哪一版标准，以及是否使用自评、互评或师评。
- “课堂教学”负责在合适的时候开启评价、完成评价和查看结果。

评价使用 1-5 星。每颗星都要有具体表现说明，不能只写“优秀、良好、一般”。如果学生没有提交作品，或本节课没有观察到相关表现，老师可以选择“暂不评价”，系统不会把它当成 1 星或 0 分。

自评、互评和师评分别保存，不会互相覆盖。评价发布后会保留历史版本，已经使用过的课堂不会因为老师后来修改标准而发生变化。

### 题库与测试

题库分为“我的题目”和“共享题库”。

- 老师自己建立的题目直接进入“我的题目”，本人组卷不需要审核。
- 老师主动申请共享后，题目才进入学校审核流程。
- 其他老师可以查看和使用已经开放的学校共享题目。
- 老师可以用 XLSX 批量导入，也可以使用自己的 DeepSeek API 批量生成题目草稿。

组卷后可以选择随机题目顺序和随机选项顺序。测试开始后，学生才能进入作答；客观题可以自动评分，主观题和附件任务由老师批阅。

## 关于课时和“第 n 周”

课堂绑定的是“课时”，不是固定周次。系统不限制课程只能有 8 周或 8 个课时。

开发数据中出现的“第 n 周学习任务”只是模拟出来的课时名称，不是老师必须填写的字段。正式使用时，老师可以按教学内容命名课时，例如“认识数据”“循环结构练习”或“项目成果交流”。

新建课堂时可以搜索课时名称和序号，课时较多时列表会在自己的区域内滚动，不会把整个表单拉得很长。

## 四类账户分别做什么

### 超级管理员

超级管理员负责维护多所学校、学校管理员账户、数据包导入、跨校汇总和系统运行情况。成员校不需要一直连接某个公共云平台；学校可以在需要时导出经过处理的数据包，再交给总平台汇总。

### 学校管理员

学校管理员负责本校教师、学生、班级、任课关系和学科前测，也负责检查学校数据是否正常、查看模型训练记录和发布状态。

学校管理员不代替老师制定课堂评价，也不直接处理每名学生的教学分层。个体建议由任课教师查看和确认。

### 教师

教师负责本人课程、课时、课堂、学生、题库、测试、评价、资源、公告和留言。教师只能查看自己的任教班级，可以查询学生账号，也可以把学生密码重置为 `123456`。

### 学生

学生端以课程学习和课堂参与为主，不使用管理后台式界面。新生首次登录后可以修改密码、选择班级，并完成相应学科的前测，再进入后续课程。

## 为什么要记录学习过程

只看一次考试成绩，很难知道学生是在什么地方遇到困难。STRATA 会记录与教学直接相关的过程，例如：

- 老师给学生投放了哪些资源、题目和任务。
- 学生是否开始、是否完成、用了多长时间。
- 第一次作答和修改后的作答有什么变化。
- 学生是否按时提交任务和附件。
- 自评、互评和师评分别给出了什么信息。
- 学生参加了哪些课堂活动和小组任务。
- 老师提供过哪些提醒、讲解或额外支持。

这些记录先用来帮助老师看清课堂情况，再考虑是否能够用于后续研究。平台不会把“点击多、在线久、聊天多”直接解释成能力强、态度好或核心素养高。

## 用老师能理解的方式说明科研设计

### 第一步：先确认记录可靠

模型训练前，系统先检查学习记录本身有没有问题，例如：

- 同一条记录是否重复写入。
- 记录是否缺少学生、课程、课时或任务信息。
- 学生设备离线后，记录是否很晚才补传。
- 新旧两套记录是否能够对应。
- 学生是否真的得到过相应的学习任务。

这项检查只判断“数据能不能继续使用”，不评价学生好坏，也不会影响学生积分和层级。检查结果只给学校管理员查看。

### 第二步：每个比例都说清楚“总数是什么”

例如，任务完成率不能只看学生完成了几项，还要知道老师一共布置了几项：

```text
任务完成率 = 已完成的有效必做任务数 / 已经到期的有效必做任务数
```

资源完成率要看老师实际投放了多少个必看资源；正确率要看有多少道题真正有明确答案。这个“总数”就是研究中常说的分母。

以下情况不能都记成 0：

- 老师没有布置相应任务。
- 学生还没有开始。
- 学生正在完成，结果尚未形成。
- 设备离线，记录还没有传回来。
- 记录有错误，需要管理员核对。
- 可用题目或任务太少，暂时不能判断。

系统会分别保留这些原因。这样老师看到的低完成率，才不会其实只是“本周没有布置任务”。

### 第三步：把评价放回具体任务

核心素养、学习策略和协作表现不能根据一次点击得出结论。老师需要结合具体作品、作答、项目过程和课堂观察来评价。

平台支持老师从以下方面选择评价内容：

- 学习成果是否达到目标。
- 学生使用了什么方法和策略。
- 遇到困难后是否有调整和反思。
- 小组协作中是否完成了自己的责任。
- 是否表现出本学科要求的实践能力。

并不是每节课都要把这些内容全部评价。老师只选择本次任务真正能够观察到的方面。签到、在线时长和课堂积分不能直接当成核心素养评价。

### 第四步：保留一部分所有学生都完成的共同题

分层教学可以给不同学生安排不同难度的任务，但如果所有题目都不一样，就很难判断学生的进步，也不能直接比较不同层次的原始分数。

因此题目分为：

- **普通题**：日常练习和课堂使用。
- **共同题**：所有学生在相近条件下完成，用来观察共同学习目标。
- **分层题**：分别面向 A、B、C、A/B 或 B/C 的差异化任务。

分层题不能代替共同题。A 层学生完成高难题得到 6 分，C 层学生完成基础题得到 6 分，这两个 6 分不能直接解释成掌握程度完全一样。

题目会保留版本。系统可以统计答对率、难度、区分情况和各选项人数；真实作答人数少于 30 时，只提示“数据不足”，不急着下结论。

### 第五步：只使用当时已经知道的信息

每次分析都要先确定一个时间点。系统把这个时间点之前已经发生、也已经传到服务器的记录保存下来，然后等待后续 7 天等学习结果形成。

这样做是为了避免一个常见错误：用学生后来才产生的成绩，反过来预测他之前的情况。

同一批数据会保存版本和校验信息。研究人员以后重新运行时，应该得到相同结果。导出的研究数据使用匿名编号，不包含学生姓名、账号和学号。

### 第六步：分开看不同问题

平台不会把所有信息简单加成一个“综合能力分”。以下问题需要分别分析：

- 学生对共同学习内容掌握得怎样。
- 学生和自己过去相比有没有进步。
- 接下来一段时间能否完成必做任务。
- 是否可能新增逾期任务。

目前已经跑通的是“随后 7 日任务完成情况”和“随后 7 日新增逾期任务”。这两项只能帮助老师判断是否需要提醒、检查计划或提供支持，不能当作学科掌握层级。

正式的内容分层还需要共同测试、共同题、知识点覆盖、测量版本和学科组确认的标准。

## 动态分层怎样理解

A/B/C 不是给学生贴上的永久标签，而是老师安排当前学习内容时使用的内部代码：

| 内部代码 | 老师安排内容时的含义 |
| --- | --- |
| A | 拓展挑战 |
| A/B | 拓展与核心之间的过渡 |
| B | 核心发展 |
| B/C | 核心与基础之间的过渡 |
| C | 基础提升 |

同一名学生在不同学科、课程或时间可以有不同建议。学生只看到自己的学习目标、任务、资源和教师反馈，不会看到代码、预测概率或排名。

正式调整不能只看最近完成率，也不能因为一次答错就变化。系统会考虑共同学习内容、近期变化、数据是否充足和建议是否稳定，并加入以下保护：

- 需要连续出现相近证据，不能一次波动就调整。
- 调整后保留一段观察时间，不能频繁上下变化。
- 一次最多调整一级。
- 证据不足时显示“暂不建议”。
- 最终由任课教师确认，老师可以接受、调整、拒绝或以后再处理。

学生的课堂积分、老师以前手工填写的层级和班内排名，都不能直接当成模型训练的正确答案。

## 动态分组怎样理解

分层和分组不是同一件事。学生需要什么难度的内容，不代表每次都要和同一层次的同学分在一组。

老师可以根据任务选择：

| 页面名称 | 更适合的课堂情况 |
| --- | --- |
| 随机组合 | 一般交流、打破固定搭配 |
| 学习进度接近 | 同步练习、分层指导 |
| 相邻互助 | 让差异不过大的学生互相帮助 |
| 特长互补 | 项目需要不同技能和角色 |
| 项目固定组 | 项目周期较长，需要保持成员稳定 |

系统会给出多个候选方案，同时考虑每组人数、历史同组次数、设备条件、角色需要，以及老师设置的必须同组或不能同组关系。老师调整并确认后才生效。

学生只看到中性组名和本组成员，不会看到“高层组、低层组”或算法依据。小组任务进行中原则上不频繁换人，需要调整时尽量放在任务阶段之间。

## 模型是怎样训练的

### 不是每班从零训练一个复杂模型

一个班只有几十名学生，直接为每班训练一套复杂模型很容易记住测试数据，却不能稳定用于下一批学生。

目前采用的做法是：

```text
学校或学科的基础模型 + 每个班级自己的校正参数 + 教师设置
```

基础模型从较完整的数据中学习共同规律；班级校正参数处理不同班级在教学进度、任务安排和完成习惯上的差异。这就是当前“一班一模型”的实际含义。

### 不只试一种算法

每次训练会把 CatBoost、LightGBM 与几种简单方法放在同一批数据上比较：

- 全体学生平均值。
- 少量清楚指标组成的透明规则。
- 常见的线性或逻辑统计方法。
- 考虑班级差异的统计方法。
- CatBoost 和 LightGBM 结构化机器学习模型。

复杂模型如果没有稳定超过简单方法，就没有必要启用。可用于测试的记录少于 30 条时，不启用高级模型。

### 学校管理员看到的指标是什么意思

| 页面指标 | 通俗解释 |
| --- | --- |
| MAE | 平均每次预测与实际结果差多少 |
| MSE | 对较大误差更敏感的平均误差 |
| RMSE | 和原结果使用相近单位，便于理解的大误差指标 |
| R² | 相比只看平均值，模型解释了多少变化；越高不代表教学效果越好 |
| 覆盖率 | 有多少学生得到有效预测，有多少因为证据不足被暂缓 |
| 校准情况 | 模型说“可能性较高”时，实际是否真的更常发生 |
| 残差分布 | 模型在哪些学生或班级上容易高估或低估 |

这些指标只评价预测是否可靠，不能证明动态分层已经提高学习成绩。

### 怎样避免模型只在测试数据上好看

系统会分别检查：

- 用较早时间训练，预测较晚时间。
- 某些学生完全不参加训练，只用于测试。
- 某些班级完全不参加训练，只用于测试。
- 使用另一所学校的兼容数据测试。
- 课程或共同测试有第二个版本时，检查换版本后是否仍然可靠。

还会故意打乱结果、加入无意义匿名编号，检查模型是否利用了未来信息或数据错误字段。检查不通过时，候选模型不能发布。

## 夜间任务会做什么

学校服务器可以在夜间自动完成：

1. `01:30` 检查前一天的学习记录是否完整。
2. `02:50` 整理已经到时间的学习情况，并更新已经形成的后续结果。
3. `03:10` 比较统计方法和模型，生成新的候选版本。

夜间任务只生成候选版本，不会自动替换当前模型。学校管理员也可以选择一批已经准备好的数据手动训练。

发布前，系统会检查数据状态、模型文件和校验码。发布失败时继续使用原版本；历史版本可以校验后回滚。教师只有在学校管理员发布候选后，才能看到本人任教班级的建议。

## 我们怎样判断研究做到哪一步

项目把结论分成七步，避免把“程序能运行”说成“教学一定有效”：

| 阶段 | 需要回答的问题 |
| --- | --- |
| C0 | 学习记录是否正确保存？ |
| C1 | 完成率、正确率等指标能否稳定重复计算？ |
| C2 | 这些指标是否真的能说明某种学习表现？ |
| C3 | 模型能否预测事先约定的后续结果？ |
| C4 | 建议是否帮助老师做出更好的判断？ |
| C5 | 使用这些建议是否真正改善了学生学习？ |
| C6 | 换到其他学校、学期和学生后是否仍然成立？ |

目前平台主要完成了 C0-C1 的工程闭环，并用模拟数据检查了 C3 所需程序。C2-C6 仍需要真实课堂、正式量表、共同测试、教师使用研究和跨校验证。

## 后续科研怎样开展

研究不会一开始就让模型直接干预课堂，而是按以下顺序推进：

1. **影子运行**：模型在后台生成建议，老师正常教学，不自动改变学生任务。先检查数据、模型稳定性和教师工作量。
2. **测量研究**：检查评价标准、共同题和学习指标能否稳定反映预期内容。
3. **预测研究**：提前写明研究问题、样本、结果和分析方法，再比较模型的预测、校准、公平性和跨校表现。
4. **教师决策研究**：比较老师独立判断、模型单独建议和老师结合建议三种情况。
5. **教学效果研究**：前面通过后，再按班级或教师开展集群随机、阶梯楔形等研究，判断教学调整是否真正产生学习增益。
6. **外校复验**：在不同学校、学期和学科中重新检查，明确可以使用和应该停用的范围。

目标投稿方向包括 *Computers & Education*。但是，页面完成、模型指标较高或老师愿意采用建议，都不能直接代替教学效果证据。

## 伦理、隐私和学生权益

- 未成年人学习数据默认保存在学校内部。
- 教师只能查看自己的任教范围，学校管理员主要查看学校汇总和运行情况。
- 学生和监护人应知道收集哪些数据、用于什么目的、保存多久，以及如何申请更正。
- 学生拒绝参加科研分析时，不应失去正常课程学习机会。
- 外部 AI 不接收学生姓名、账号、原始答卷、聊天、学习档案和内部层级。
- 跨校数据包默认去除姓名、账号和学号，也不直接包含聊天原文、答卷正文和作品文件。
- 学生可以申请更正身份、班级和任务匹配错误。
- 系统不得自动调班、自动降级、自动处分或自动扣分。
- 人数很少的群体不输出不稳定比较，避免通过组合信息重新识别学生。

正式学校试用前，需要完成学校和伦理审批、未成年人及监护人同意、教师培训、研究预注册、数据保存期限和退出流程。

## 私有化部署

- 页面、ECharts 和系统业务资源都从学校服务器本地提供，不使用 CDN 或公网字体。
- 开发和单机体验可以使用 SQLite；学校正式部署建议使用 PostgreSQL。
- Redis 用于实时课堂消息和后台任务。
- 学生电脑只需要浏览器，不需要逐台安装 Python、Node.js 或数据库。
- ONLYOFFICE 和 DeepSeek 都是可选能力，不影响基础教学流程。

## 给开发和维护人员

### 技术组成

- Python 3.12
- Django 5.2 LTS + Django REST Framework
- Vue 3 + TypeScript + Vite
- PostgreSQL 16/17
- Redis + Celery + Django Channels
- ECharts

业务页面由 Vue 提供，Django 负责接口、权限、数据库、文件、后台任务和 WebSocket。

### 运行关系

```text
教师 / 学生 / 管理员浏览器
          |
          +-- Vue 页面 --HTTP--> Django REST API --+--> PostgreSQL
          |                                        +--> 本地文件
          |
          +-- WebSocket -------> Django Channels -----> Redis

学校后台定时任务 -------------> Celery + Redis -------> 数据检查、汇总和模型候选

可选：Django <---------------> ONLYOFFICE Document Server
可选：教师主动使用 -----------> 教师自己的 DeepSeek API
```

接口说明见 [API 契约](docs/api_contract.md)，数据关系见 [数据模型](docs/data_model.md)，Vue 目录和组件规则见 [前端架构](docs/frontend_architecture.md)。

### 运行前准备

当前脚本主要面向 Windows PowerShell。开发机需要 Python 3.12；修改 Vue 源码时需要 Node.js 和 npm；学校正式部署需要 PostgreSQL 和 Redis。

从示例创建本机配置：

```powershell
Copy-Item .env.example .env
```

正式部署前需要修改 Django 密钥、AI 加密密钥、数据库密码、允许访问的主机和 Redis 配置。`.env`、数据库密码、教师 API Key、模型签名私钥和隔离区密钥不能提交到 Git。

### 第一次安装

使用项目内准备的离线 Python 依赖包：

```powershell
.\scripts\install_offline.ps1
```

初始化或更新数据库：

```powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py sync_learning_event_schemas
.\.venv\Scripts\python.exe manage.py sync_analysis_definitions
```

### 启动系统

只在本机开发：

```powershell
.\scripts\run_dev.ps1 -Port 8010
```

允许同一局域网的电脑访问：

```powershell
.\scripts\run_lan.ps1 -Port 8010
```

在服务器后台运行：

```powershell
.\scripts\start_lan_background.ps1 -Port 8010
```

访问地址：

```text
http://127.0.0.1:8010
http://<学校服务器的局域网 IP>:8010
```

`run_lan.ps1` 和后台脚本通过 Uvicorn 启动 Django ASGI，支持 WebSocket。正式部署不能只使用 Django 开发服务器。

### 构建 Vue 前端

```powershell
cd frontend
npm.cmd install
npm.cmd run build
cd ..
```

构建结果写入 `static/frontend/`。只有开发机需要 Node.js，普通教师机和学生机不需要安装。

### PostgreSQL 和后台任务

切换 PostgreSQL 配置：

```powershell
.\scripts\switch_to_postgres.ps1
```

启动 Celery Worker 和定时任务：

```powershell
.\scripts\run_celery_worker.ps1
.\scripts\run_celery_beat.ps1
```

正式学校环境需要把 Django ASGI、Redis、Celery Worker 和 Celery Beat 作为独立服务运行，并设置开机启动和日志轮换。

没有真实教学数据时，可以生成一批能够整批清理的模拟数据，用于检查页面、统计和训练流程：

`--weeks` 支持 `1-52`，它只表示模拟数据覆盖多少周，不是课程课时上限。先加 `--dry-run` 可以只查看预计生成量。清理方法见 [模拟数据说明](docs/synthetic_data_research_track.md)。
