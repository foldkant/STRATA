## 1. 本轮准确边界

本轮只完成 P0—P1，不提前实现后续阶段。

| 阶段 | 本轮完成内容 | 本轮明确不做 |
| --- | --- | --- |

## 2. P0 冻结的教育语义

### 2.1 评价、学习状态、内容带与分组不是同一对象

```text
评价方案与评价标准
  → 学生在具体任务中的个人或小组评价材料
  → 合格的评价结果及其适用范围
  → 目标级、带不确定性的学习状态
  → 教师审核的内容带建议

具体任务、学习目标、成员条件和学习机会
  + 可用于该任务的学习状态或角色信息
  → 分组候选方案
  → 教师确认的分组计划
```

必须遵守以下边界：

1. 评价不是测试的同义词。测试、操作、实验、项目作品、展示、答辩、学习过程材料和迁移任务都可以提供评价材料，但必须分别说明适用目标和证据局限。
2. 评价结果不能直接等同于稳定能力。一次任务只支持对该任务和相应学习目标的判断；跨任务状态需要多个合格且可比较的个人证据。
3. 学习状态不是内容带。学习状态描述当前目标级表现及不确定性；内容带是教师在特定教学窗口内确认的教学安排。
4. 内容带不是分组。分组必须针对具体任务、阶段、角色、资源与安全约束生成，不能把 A/B/C 排队复制成小组。
5. “动态”表示有足够新证据、到达合法更新时点并经过教师确认后才更新，不表示每次点击、每次评分或每天自动换层、换组。
6. 小组作品只能形成小组层面的结果。要更新个人学习状态，必须有可以归属于个人的作答、操作、说明、答辩或其他个人评价材料。
7. 兴趣、态度、自我效能、缺席、设备条件、无障碍安排、求助、签到、积分和在线时长不得与学科表现相加后用于降低内容带。
8. “未参加、未投放、未评分、材料不足、技术问题、不适用于当前任务”必须分别记录，不能补成 0 分、1 星或最低内容带。
9. 教师采纳记录、当前内容带和系统历史建议不得回流成为模型自己的正确答案。
10. 决策后的反馈、支架、分组、同伴、修订和结果不得作为决策前特征使用。

### 2.2 对课程标准的使用边界

课程标准结构统一按以下四类教育内容管理：

- 核心素养；
- 课程目标；
- 课程内容；
- 学业质量。

四类内容之间存在多向、层级化关系，不能简单拼成一条自动计分公式。平台必须避免以下跳跃：

```text
课标原文 → 自动生成一个核心素养分数 → 自动分层 → 自动分组
```

P1 只建立权威来源和可追溯的课程标准内容条目。未来评价设计仍需由教师根据课程内容明确学习目标、评价依据、学习任务和评分规则；课标原文引用本身不证明评价有效，也不证明学生已经达到相应核心素养要求。

### 2.3 角色责任

| 角色 | P0—P1 责任 | 明确禁止 |
| --- | --- | --- |
| 超级管理员 | 管理课程标准文件、来源、版本、解析结果、复核记录、发布状态、当前使用版本和历史恢复 | 不代替教师制定成员校的评价内容；不修改学生评价结果；不把未复核解析结果直接用于正式评价 |
| 课标复核人员 | 对结构化文本、内容条目类别、层级关系和原文位置进行复核并留痕 | 不以 AI 摘要或个人改写替换权威原文；正式使用前不能由同一人员完成全部独立复核环节 |
| 教师 | 后续阶段选择已发布课标版本和内容条目，制定并审核评价方案、评价标准及课堂使用方式 | 不直接修改已发布课标；不把课程标准内容条目直接当作学生得分 |
| 学校管理员 | 后续查看本校使用情况和运行汇总 | 不编辑教师评价标准；不编辑国家课程标准内容 |
| 学生 | 后续查看教师公开的学习目标、评价要求和本人结果 | 不接触内部内容带、模型参数、他人评价材料或分组优化信息 |
| 系统或 AI | 当前仅保存、解析、检索和提示待复核内容；AI 生成功能尚未开放 | 不自动发布课标；不自动确认课标对齐；不自动评分、分层或分组 |

正式使用的发布流程应保留职责分离：导入/整理、内容复核和最终发布分别留存操作者与时间。开发环境允许使用测试账号验证状态流转，但不能据此声称已经完成独立专家复核。

### 2.4 首期伤害登记与处置责任

P0 不是只统一栏目名称，还要明确哪些错误不能被总体平均成绩或模型性能抵消。

| 可能伤害 | 首期预防规则 | 发现后的最低处置 | 责任主体 |
| --- | --- | --- | --- |
| 错误降低学习内容层级 | 证据不足时暂不建议；降低层级需要更严格的材料、说明和教师复核 | 停止相应建议，恢复教师人工安排，核对受影响学生的学习机会 | 任课教师、学校管理员、模型发布责任人 |
| 挑战性学习机会被长期减少 | 所有层级保留共同核心目标与最低学习机会；跟踪实际投放而非只看计划 | 补充学习机会，暂停造成机会收窄的层级标准或分组策略 | 任课教师、课程负责人 |
| 分层或分组造成公开标签与污名 | 学生端只显示实际任务、支持和中性组名，不显示内部 A/B/C、风险或算法依据 | 立即关闭泄露界面/导出，通知并更正，执行隐私事件记录 | 产品与安全责任人、学校管理员 |
| 小组角色排斥或个人贡献被小组成绩覆盖 | 分组服务具体任务；组级材料与个人材料分开；可访问性调整不得记为能力不足 | 教师调整角色和支持，补充个人表达机会，撤回不当个人结论 | 任课教师 |
| 隐私、越权或学生数据外发 | 对象级权限、最少数据和访问审计；外部 AI 不接收未经授权的学生级材料 | 中止相关接口或 AI 调用，保全审计记录，按事件流程处置 | 系统安全责任人、数据管理责任人 |
| 因持续“暂不建议”而无人支持 | 暂不建议必须关联可执行的补充材料或人工核查路径 | 建立教师待办并在规定时间复核，不能让学生永久停留在无结论状态 | 任课教师、年级/课程负责人 |
| 频繁换层、换组破坏学习稳定性 | 只在合法决策点更新；阶段内默认稳定；紧急安全调整走独立路径 | 回退到上一已确认安排或教师人工安排，并记录原因 | 任课教师、策略发布责任人 |
| 教师复核负担超过实际容量 | 发布前统计待办量、处理时间和拒绝后的服务路径；不以默认自动采纳消化积压 | 降低建议频率或覆盖范围，保持人工教学流程 | 学校管理者、产品负责人 |
| 测试数据污染正式训练或研究 | 测试批次隔离、可清理、导出明确标记，正式数据查询默认排除 | 停止相应分析或发布，重建未污染数据版本 | 数据与研究责任人 |

本阶段只登记伤害类型、禁止行为和处置责任，不虚构统一统计阈值。后续正式试点必须针对不同伤害分别预先确定观察指标、判断标准、暂停范围和申诉渠道；“总体表现不错”不能抵消任何不可接受的个体安全、机会或隐私问题。

产品账号角色不能替代研究职责。进入真实试点前，还必须书面指定学科内容复核、评价方法、数据管理、统计分析、伦理与隐私、软件版本和学校现场实施的负责人。同一开发人员可以完成工程测试，但不能把自己的测试结果冒充独立学科复核、统计复核或外部验证；同一批用于修改规则的测试数据也不能再作为确认性效果数据。

## 3. P1 数据与版本规则

### 3.1 每个课程标准版本必须保存

- 学段：`K1-K9` 或 `K10-K12`；
- 学科和适用范围；
- 正式名称、发布/修订年份、官方来源地址和来源说明；
- 原始 PDF 或受控文件引用、文件大小和 SHA-256 文件哈希；
- 可检索的逐页文本，且能够回到页码；每页同时保存提取方式、字符数、内容校验值和复核状态，文字识别页还需保存识别置信度；
- 结构化内容条目的类别、标题、正文、顺序、上下级关系和原文位置；
- 解析方式、解析版本、解析时间、人工复核状态及复核人；
- 草稿、待复核、已发布、已取代或已归档等生命周期状态；
- 当前使用版本关系、替代关系和全部操作记录。
- 供后续检索使用的页码化 Markdown、单个结构化 JSON 与流式 JSONL 输出；每条机器可读记录必须包含课程标准版本、文件校验值、内容条目校验值和原文位置，不能只输出脱离来源的纯文本。

结构化内容条目必须至少支持“核心素养、课程目标、课程内容、学业质量”。PDF 中无法可靠识别的页面或段落必须标为待复核，不能生成看似确定的正式内容条目。版本进入正式发布前，必须能够核对逐页处理状态；需要文字识别、识别置信度较低或内容为空的页面必须由独立复核人员明确确认，处理失败页则必须修复后才能发布，均不得被静默视为已复核。

### 3.2 版本不可变与恢复规则

1. 草稿和解析中的内容可以更正；发布后版本及其原始文件哈希不得原地改写。
2. 新文件或修订版必须新建版本，不覆盖旧版本。
3. “当前使用版本”只是指向某个已发布版本的关系，不是复制文件，也不是名为 `current` 的永久权威版本。
4. “恢复”表示把某个历史已发布版本重新设为当前使用版本，并生成新的操作记录；不得删除后续版本，也不得改写历史引用。
5. 已被评价方案、课堂或研究数据引用的版本不得物理删除；停用时标记为已取代或已归档。
6. 版本比较至少展示基本信息差异、文件哈希变化、结构化内容条目的新增/删除/修改和原文位置变化。
7. 历史评价、课堂与研究记录始终指向当时使用的具体版本，不能在课标更新后静默跟随新版本。

| 教育业务对象 | 工程对象 | P0—P1 用途 |

| 课程标准内容条目 | `CurriculumStandardNode` | 保存四类正式内容、上下级关系、原文位置和内容校验值 |
| 操作记录 | `CurriculumStandardAuditLog` | 记录导入、提交复核、逐页复核、版本复核、发布、归档和恢复等动作 |

| 已发布评价方案引用快照 | `EvaluationPlanVersionCurriculumReference` | 冻结课程标准版本和内容条目校验值，避免后续课标更新改写历史评价 |

课程标准版本状态按“草稿 → 待复核 → 已复核 → 已发布/已归档”流转。创建或提交人员不能复核本人版本，发布人员不能与复核人员相同；所有逐页文本也必须由与创建/提交人员不同的人员确认。该职责分离是正式发布门槛，不是只有界面提示的建议。

## 4. 测试数据迁移规则

用户已授权直接修改现有测试数据。该授权不改变正式数据保护规则。

### 4.1 可以迁移

- 带 `[TEST]`、`SIM-`、独立合成批次标记或能够由既有测试命令完整识别并清理的数据；
- 现有测试评价方案、评价标准及其已发布测试版本；
- 现有测试用动态分层候选、教师模拟处理记录、分组候选和分组计划；
- 为 P1 权限、版本、内容条目、比较和恢复流程新增的测试课标数据。

### 4.2 迁移方法

1. 迁移前保存测试批次标识、原主键、数量和内容摘要。
2. 能可靠映射到新字段的内容按明确规则迁移，并保存迁移批次和来源标记。
3. 无法可靠映射到课程标准内容条目或原文位置的旧学习目标继续保留为历史教师文本，标记为“未建立课标引用”，不得伪造引用。
4. 旧评价、状态和分组记录不得因为字段缺失被补成正式有效结论。
5. 迁移脚本必须可重复运行；重复执行不能制造重复版本、内容条目或引用。
6. 清理只能按完整测试批次执行，不能依靠模糊标题删除正式数据。
7. 测试数据可用于页面和状态流转验收，不得进入正式模型训练、正式学校统计或科研结论。

### 4.3 不得修改

- 无明确测试标记的正式学生评价、作答、作品和教师决定；

### 5.3 后台任务运行边界

课程标准 PDF 处理使用独立的 `curriculum_ocr` 队列。一个任务只处理一个版本；专用 worker 固定 `concurrency=1`、`prefetch=1`，普通 Celery worker 只监听默认 `celery` 队列。任务进度、取消状态、失败原因和最终结果以数据库为唯一真值，Celery result backend 不参与课程标准治理判断。

本地无 Redis 的 Windows 开发环境使用单机 filesystem transport，消息目录固定为 `storage/celery/curriculum_ocr/` 下的 `producer-out`、`worker-out`、`processed` 和 `control`。Web/API 使用 `producer` 方向，专用 worker 使用 `worker` 方向；两者配置不一致时不得声称任务已经入队。该方案不用于学校生产环境；生产必须使用 Redis、独立 worker 和操作系统级 CPU/内存约束。

管理员可以取消排队任务；运行中任务转为“取消中”，worker 在页级安全点终止。停止 worker 前，停止脚本会只读检查数据库并在存在 `running/cancelling` 时拒绝普通停止。worker 异常退出时，平台根据心跳把失联任务标为失败，保留原正式逐页文本，之后由管理员显式重试；不得因进程退出自动把半成品发布为课标内容。
