# 详细问题与工程证据

## 一、P0：上线或扩大试用前必须处理

### 1. 资源文档回调缺少签名校验，并存在服务器代请求风险

`resource_office_callback` 使用 `csrf_exempt` 和 `AllowAny`，随后直接读取匿名请求中的 `url`，通过 `urllib.request.urlopen` 下载并覆盖资源附件。该流程没有调用项目已经具备的 `verify_callback_payload`，也没有限制下载主机、协议和文件大小。

证据：

- `api/resource_views.py:440`：匿名、免 CSRF 的资源回调。
- `api/resource_views.py:455`：直接请求回调提供的 URL。
- `api/classroom_views.py:2306`：小组协作文档回调已经具备 JWT、文档键和版本校验，可作为修复依据。
- `config/settings.py:352`：OnlyOffice JWT 密钥默认允许为空。

改进要求：

1. 资源回调与小组协作文档回调统一使用 JWT 验签，并核对 `status`、`key`、`url`。
2. 只允许配置的 OnlyOffice 服务地址；拒绝本机地址、私网跳转和非 HTTP(S) 协议。
3. 限制响应大小、超时、重定向次数和文件类型。
4. 先保存不可修改的新版本，校验哈希成功后再切换当前版本。
5. 生产环境缺少 `ONLYOFFICE_JWT_SECRET` 时启动失败，而不是退化成无签名模式。
6. 增加伪造签名、错误文档键、超大文件、重定向和服务器代请求测试。

### 2. 课堂已投放资源与资源可见范围的权限模型不一致

学生课堂 3 已展示资源“演示文稿1 (1)”，但请求 `/api/v1/resources/2/office-config/?mode=view` 返回 404。资源文件和数据库记录都存在，问题来自权限判断：学生只能通过资源的全局可见范围、班级共享范围或跨校发布范围获得访问权，没有把“当前课堂已经投放给该班级”作为只读授权依据。

证据：

- `api/resource_views.py:323`：学生资源可见范围条件。
- `api/resource_views.py:341`：资源打开权限判断。
- `api/resource_views.py:377`：Office 预览入口。
- [学生课堂截图](screenshots/student/classroom-3--desktop.png)
- [学生评价流程截图](workflow-screenshots/student/classroom-evaluation.png)

建议把权限拆成两层：

- 资源库可见：决定学生能否在资源中心搜索到资源。
- 教学情境授权：课程、课时或正在进行的课堂已经投放时，任课班级学生获得只读访问；课堂关闭或撤回后按保存的教学记录决定是否继续可见。

必须补充教师本人、任课班级学生、同校非任课学生、其他学校学生、课堂已结束等权限测试。

### 3. 生产安全配置没有形成“拒绝不安全启动”的边界

`manage.py check --deploy` 返回 6 项提醒：未设置 HSTS、未强制 HTTPS、密钥强度不足、Session Cookie 与 CSRF Cookie 未设为仅 HTTPS、DEBUG 仍开启。登录接口也没有发现请求限流或账号失败锁定机制。

证据：

- `config/settings.py:41`：开发密钥默认值。
- `config/settings.py:69`：DEBUG 默认开启。
- `config/settings.py:352`：OnlyOffice 密钥默认空。

建议建立 `settings/base.py`、`settings/development.py`、`settings/production.py`，在 production 中校验全部必需环境变量；增加登录限流、失败次数审计、短时退避和管理员解锁机制。

## 二、P1：直接影响教师与学生能否顺畅完成任务

### 4. 教师端信息架构按“功能模块”排列，而不是按“教学工作”排列

教师端有 13 个并列导航入口。评价、题库、测试、资源、协作文档、AI 接入和分层建议彼此平行，一线教师需要先理解平台结构，才能判断本节课该去哪里。

证据：`frontend/src/views/teacher/nav.ts:1`。

建议将主要入口压缩为：

1. 今日工作
2. 课程与课时
3. 课堂实施
4. 作业与测评
5. 学生学习情况
6. 教学资源
7. 沟通协作

AI 应嵌入备课、出题、评价和反馈环节，不应作为教师必须理解的独立业务模块；AI 服务配置移到个人设置。评价方案库保留为复用、历史版本和质量记录入口，具体课时评价继续在课时设计内完成。

### 5. 教师复杂任务过度依赖大弹窗

抽查的 21 个教师操作流程中，20 个打开弹窗；12 个弹窗高度达到视口的 80% 以上，6 个达到 90% 以上。“课时评价→手工新建”和“课时评价→AI 辅助起草”还同时保留父子两个对话框。

主要影响：

- 教师难以判断自己仍位于哪个课时和环节。
- 页面滚动与弹窗滚动并存。
- 刷新、误关闭或返回时容易丢失上下文。
- 双层对话框增加键盘焦点和屏幕阅读器处理难度。

证据：

- [教师功能流程总览](contact-sheets/teacher--workflows.jpg)
- `frontend/src/components/teacher/LessonStepEvaluationModal.vue:421`
- `frontend/src/components/evaluation/EvaluationAIDraftWizard.vue:1`

处理原则：

- 简单新增、确认使用弹窗。
- 超过一个步骤或超过 8 个字段的任务改为页内工作区、右侧抽屉或独立页面。
- 复杂流程固定显示“当前课时—当前环节—保存状态—下一步”。
- 自动保存草稿；返回课时后恢复原位置。
- 不保留两个同时具有 `role="dialog"` 的嵌套对话框。

### 6. 移动端“没有撑破页面”，但后台表格仍不可高效使用

首轮没有发现整页横向溢出，但学校、教师、学生、班级、任课关系等表格在 390px 宽度下被放进内部滚动区或压成窄列。用户只能看到前几列，行末操作不可同时理解。37/50 个页面存在小于推荐触控面积的可见控件，学生、班级和教师列表最集中。

证据：

- [学校管理员手机端总览](contact-sheets/school-admin--mobile.jpg)
- [教师手机端总览](contact-sheets/teacher--mobile.jpg)
- `frontend/src/styles/main.css:1`：现有全局样式文件。

建议：

- 手机端把每行改为摘要卡：姓名/班级/状态为主信息，其他字段折叠，“更多”打开操作底部面板。
- 高频操作触控区域不小于 44×44px；复选框扩大点击标签，不只放大方框。
- 批量选择使用固定底部操作栏。
- 桌面端保留表格，手机端不强行保持相同布局。

### 7. 学生存在可进入但未形成任务闭环的页面

学生“任务”和“项目”当前是占位页，教师“项目学习”也是占位页。学生首页却把“任务”作为可到达入口，容易让学生认为没有任务或平台故障。

证据：

- `frontend/src/router/index.ts:87`
- `frontend/src/router/index.ts:136`
- `frontend/src/views/student/ModulePlaceholderView.vue:1`

建议在功能完成前隐藏入口或标明“建设中且不影响当前学习”；更好的做法是先实现统一任务流，将课堂题、测试、作品、评价和补充学习按“待完成—即将截止—已完成”汇总。项目学习先放在课程详情内，待跨课程项目足够多时再建立全局项目中心。

### 8. 被课堂接管或尚未投放的页面，恢复路径不够明确

学生直接访问课时工作区时收到 403，页面顶部能说明“请从课堂入口进入”，但主体仍停留在“正在加载课时内容”；直接访问未投放学习网页也产生 403。权限边界本身合理，页面状态不应表现为失败或持续加载。

建议：

- 被课堂接管：显示当前课堂名称和“进入课堂”主按钮，可安全时自动跳转。
- 尚未投放：显示“教师尚未投放”，只保留返回课程，不继续重试。
- 无权限：不要把 403 写入控制台作为未处理错误。

### 9. 禁用操作缺少原因

基线页面共发现 77 个可见禁用按钮，没有一个提供 `title` 或 `aria-describedby`。其中课堂列表存在 41 个重复的禁用“编辑/删除”，课时设计有 9 个“上移/下移/已在当前环节”。

建议对业务状态造成的禁用给出直接原因，例如“课堂已开始，不能编辑；可复制为新课堂”。普通分页边界可以不解释，但应避免显示大量没有意义的禁用操作。

### 10. 教育管理界面暴露了过多模型工程术语

学校管理员“分层分析”直接显示 CatBoost、模型包、校验模型包、训练、漂移和技术指标。学校管理者真正需要判断的是材料是否完整、结果是否稳定、哪些班级需要复核、教师是否已经确认安排。

建议：

- “分层分析”改为“学习情况与支持建议”。
- “训练分层模型”改为“更新分析结果”。
- “模型包”改为“分析版本”。
- 默认页只呈现材料完整性、适用范围、结果稳定性、待教师确认数量和异常提醒。
- 算法、特征、性能指标放进“技术说明”，仅供平台技术人员查看。

超管最近操作中仍显示 `teacher.classroom.evaluation.toggle` 等事件代码。中文操作名称保留在主界面，代码进入展开详情即可。

## 三、性能与后端结构

### 11. 三个读接口已经出现查询量或返回体放大

使用当前测试数据、同一数据库连接进行只读查询计数：

|接口|查询数|响应体|主要问题|
|---|---:|---:|---|
|教师分层概览（课程 16，98 名学生）|109|约 28 KB|查询量随学生数近似线性增加|
|教师课堂列表|45|约 70 KB|相同关联查询最高重复 19 次|
|课程标准目录（38 项）|20|约 255 KB|同类查询重复 13 次，并返回全部嵌套数据|

原始结果见 [query-count-audit.json](query-count-audit.json)。

建议：

- 分层概览把目标学习情况、当前学科内容层级和待处理建议改为批量查询后内存映射。
- 课堂列表对课时、课程、班级、活动数量、评价配置使用 `select_related`、`prefetch_related` 和聚合注解。
- 课程标准目录只返回主档摘要和当前版本摘要，使用服务端分页；历史版本、逐页文本和内容条目在选中后加载。
- 为这些接口增加测试预算，例如分层概览不超过 20 条查询、课堂列表不超过 12 条、目录首屏响应体不超过 50 KB。

建议按业务边界继续拆分：

- API：认证与账号、课程与课时、课堂运行、评价、测试题库、资源、学生、学习起点诊断。
- 课堂前端：环节控制、资源舞台、任务面板、签到、点名、抢答、倒计时、聊天、评价、小组合作。

- CSS：基础变量、布局、表单、表格、弹窗、角色页面与各业务模块；禁止继续向单一文件追加。

### 13. AI 出题仍同步占用 Web 请求

AI 评价已使用 Celery 后台任务；题库“AI 批量出题”仍在 HTTP 请求内直接调用模型服务。

证据：

- `api/pretest_services.py:634`
- `api/assessment_views.py:818`
- `learning_analytics/services/ai_evaluation_drafting.py:1964`

建议统一为后台任务：创建任务、显示排队/生成/失败/已取消、支持重试和离开页面后恢复。超管或系统健康页应能看到各队列的积压、最长等待和失败率。

### 14. 构建资源清理机制存在，但 Git 仍被哈希文件污染

当前 `static/frontend/assets` 有 193 个文件、约 4.14 MB；清理脚本判断当前和上一版本均应保留，因此 dry-run 删除 0 个。但 Git 状态同时出现 175 个已跟踪删除与 186 个未跟踪哈希文件，说明每次构建仍会产生大批无业务意义的版本变化。

建议：

- 源代码仓库不跟踪哈希构建文件；由 CI 生成并发布构建产物。
- 若必须随应用提交，只保留一次正式发布版本，不同时保留开发机多次构建。
- 清理脚本增加最大版本数、最大保存天数和清理报告。
- 部署使用版本化目录与原子切换，回滚指向上一目录，而不是依靠 Git 中的大量哈希文件。

## 四、测试、可访问性与可观测性

### 15. 单元测试已建立，但缺少正式端到端和持续集成

当前前端有 26 个 Vitest 文件、80 项测试，评价与课程标准组件覆盖较多；51 个 Vue 页面中只有少数页面级测试。仓库没有 `.github/workflows`，临时 Playwright 脚本也没有进入正式测试体系。

建议最先建立四条端到端主流程：

1. 登录、角色权限和越权访问。
2. 课时设计中手工/AI 新建评价、保存草稿、发布并绑定。
3. 教师投放课堂任务，学生作答、评价、上传材料，教师审阅。
4. 学习起点诊断提交不可修改版本，缺失材料不记为低水平。

随后增加视觉回归、390px/768px/1440px 三档截图和自动可访问性检查。

### 16. 可访问性问题数量不大，但触控和状态说明问题普遍

明确发现：

- 资源审核搜索框缺少可访问标签：`frontend/src/views/school-admin/ResourceReviewsView.vue:94`。
- 学生课堂小组文件说明输入框缺少可访问标签：`frontend/src/views/student/ClassroomView.vue:1077`。
- 教师首页和学生课程页各有一处标题层级跳跃。
- 大量操作控件小于推荐触控面积。
- 双层评价弹窗增加焦点管理风险。

建议把可访问性要求写入公共组件，而不是逐页修补：表单控件强制标签、弹窗强制标题与焦点返回、按钮最小尺寸、错误信息关联字段、键盘可完成全部主流程。

### 17. 缺少统一运行监测

平台有操作审计和系统健康页面，但没有发现统一的结构化日志、请求关联号、异常采集或性能指标接入。发生“按钮无反应”时，目前仍主要依赖人工查浏览器和服务器日志。

建议至少记录：

- 请求编号、用户角色、路由、耗时、状态码。
- Celery 队列等待、执行、重试、取消和失败原因。
- 外部 AI 与 OnlyOffice 调用耗时、状态、供应商错误码。
- 慢查询与响应体超限。
- 前端未处理异常和失败接口。

所有监测均不得写入学生敏感文本、答案原文或内部层级标签。

## 五、测试数据与展示质量

当前测试数据包含“111”“01”“test”“123123”等低信息量名称，课堂聊天还保留不适合作为演示内容的教师发言。这会让完整功能看起来像未完成页面，也不利于教师理解评价、任务和课标之间的关系。

建议建立一套只围绕信息科技学科的标准演示数据：

- 课程：数据与计算。
- 单元：数据编码与信息表示。
- 课时：图像编码与数据量估算。
- 学习目标、学习活动、评价任务、评价指标和表现水平完整对应。
- 同时包含测试式、操作式、项目式三种评价方案。
- 学生材料包含“充分、部分、缺失、设备问题、未获得机会”五类情况。
- 聊天、留言、作品和姓名全部使用适合公开演示的内容。
